# Free Promotion Playbook

This playbook keeps launch promotion cheap, reversible, and evidence-based.
Use it only after the target repository passes `public-launch-gates.md`.

## Launch order

Current hub status: the hub is public, pinned on the owner's GitHub profile,
and the selected-MVP global closeout has passed. The sequence below remains the
reusable playbook for future public launches, downstream repositories, and
optional social announcements.

For the current MVP, broad social or video refresh no longer waits on selected
MVP closeout evidence, but it still requires an owner-approved publication gate
and a final claim review. Any claim that goes beyond the selected Skills MVP
requires a fresh public-refresh gate.

1. Publish the hub first.
2. Confirm the hub README renders correctly.
3. Pin the hub on the GitHub profile.
4. Add or confirm repository topics.
5. Publish a short GitHub profile blurb.
6. Optionally post one short social announcement.
7. Wait for feedback before publishing downstream repositories.

## GitHub profile blurb

Short version:

```text
Building a modular open-resource governance stack: resource radar, curated agent skills,
public/private configuration templates, and official-source bookmark taxonomies.
Public core, private state, verifiable automation.
```

Chinese version:

```text
正在搭建一套模块化开放资源治理体系：资源雷达、精选 agent skills、公开/私有配置模板、
官方来源书签分类。公开核心，私有状态，可验证自动化。
```

## Pinned repository order

Recommended pins:

1. `open-resource-governance`
2. `research-bookmarks-public`
3. `resource-radar-public`
4. `codex-user-config-template`
5. `claude-user-config-template`

Keep `resource-radar`, `agent-skills-curated`, and private user-configuration
repositories unpinned unless they later pass their own public gate.

Do not pin a private or not-yet-public repository as if it were available.

## Follow-up cadence

Keep the cadence light:

- one launch post;
- one short update when a downstream repository becomes public;
- one monthly or milestone-based progress note;
- no daily hype loop unless there is real evidence to share.

## Free channels

Use free channels first:

- GitHub profile;
- pinned repositories;
- repository topics;
- README links;
- release notes;
- GitHub Discussions, only when moderation capacity exists;
- short posts on existing social accounts.

Do not buy ads, domains, hosting, SaaS, or paid automation until there is real
usage evidence or a clear reason.

## Messaging boundaries

Emphasize:

- public-safe structure;
- private state;
- human approval gates;
- evidence-backed automation;
- modular reuse.

Avoid claiming:

- complete coverage;
- production-grade platform status;
- legal or security certification;
- guaranteed monetization;
- full automation without human review.

## Feedback loop

For early feedback, ask:

1. Is the public/private boundary understandable?
2. Is the repository map clear?
3. Which part is most useful: radar, skills, config template, or bookmarks?
4. What would make contribution safe and low-friction?
5. Which validation evidence is missing?

Feed answers back into issues or roadmap updates before expanding the system.
